# Pregame — Replay Determinism Audit

**Verdict (3 lines):**
1. Replay will **NOT** reliably work as shipped: the improver prompt embeds a random-uuid fragment (via the brief id -> feedback id chain), so `run_demo`'s second/third `improve()` calls will almost certainly cassette-miss on stage.
2. Everything else checked (thread-pool result ordering, sim-clock timestamps, past-proposal prompt fields) is deterministic and safe — this is one bug, not systemic rot.
3. Fix is small (change how the feedback `_id` or brief `_id` is derived) but requires a full re-record before rehearsal, since it changes cassette keys.

## Findings, ranked

### 1. CRITICAL — random brief id leaks into the improver prompt via feedback `_id` — replay will miss
- **file:line:** `pregame/drafter.py:56` (`"_id": uuid.uuid4().hex,` — unconditional, live/record/replay all take this path), `pregame/loop.py:213` (`"_id": f"fb-{event_id}-{brief['_id'][:8]}"`), `pregame/improver.py:393` (`f"- [{f.get('_id')}] {f.get('text', '')}"` inside `_live_prompt`'s "RECENT FEEDBACK FROM ADVISORS" block, which is part of the exact string hashed as the improver's `prompt` in `pregame/llm.py:62-64,109`).
- **Why it matters:** `uuid.uuid4()` is pure randomness with no seed and is not itself a cassette-recorded value — it's generated fresh by Python on every call to `draft_brief`, in every mode (fake/live/record/replay alike). Once a market event produces missed-question feedback, that feedback's `_id` (containing 8 random hex chars from the brief id) is written verbatim into the improver's system+prompt text. `run_demo`'s script (`pregame/loop.py:360-445`) fires two events, expects feedback, then calls `improve()` twice more with that feedback in context. Because the random fragment differs between the record run and the replay run, `sha256(role+model+system+prompt)` differs too, so `LLM.complete_json` in replay mode (`pregame/llm.py:108-115`) raises `LLMError: replay: no cassette entry for role 'improver'` — on exactly the "expect a policy change committed" beat, the most important moment of the demo.
- **Verified empirically** (read-only, mongomock, fake mode, no network/Atlas/CLI touched): ran `loop.setup` + `loop.make_brief` + `loop.market_event` x2 twice from two independently freshly-seeded in-memory dbs. Brief ids differed every run (`f9ffc556...` vs `469eeca8...`) and so did feedback ids (`fb-ret-rmd-age-944c7e9d` vs `fb-ret-rmd-age-b8c22282`, etc.) — 100% divergence, not a rare collision.
- **Not affected (verified safe):** proposal ids also use `uuid.uuid4()` (`pregame/gate.py:323`, `pregame/improver.py:324`) but `_live_prompt`'s "YOUR PAST PROPOSALS" block only formats `kind`/`diff`/`status`/`decision` (`pregame/improver.py:406-408`), never `_id` or `created_at` — that path is clean.
- **Smallest fix (~10-15 min):** stop deriving any prompt-visible id from `uuid.uuid4()`. Either (a) make brief `_id` deterministic — e.g. hash of `field + account_id + as_of.isoformat()` — or (b) build the feedback `_id` from `event_id` alone (plus a small deterministic counter if collisions are possible), not from `brief['_id'][:8]`. Either removes the only random value that reaches a prompt. **Must re-record `cassettes/demo.jsonl` after the fix** — old recordings were made with the buggy id scheme and their improver-role keys won't match post-fix prompts either.

### 2. Confirmed SAFE — oracle's thread pool does not reorder results
- **file:line:** `pregame/oracle.py:511-512` (`with ThreadPoolExecutor(...) as pool: results = list(pool.map(run, jobs))`).
- `Executor.map` returns results in the order of the input iterable regardless of completion order (stdlib guarantee), and `zip(jobs, results)` at `oracle.py:515` re-pairs correctly. Concurrency here does not introduce nondeterminism into which grade attaches to which scenario/run. This was the audit brief's top suspicion and it does not hold up.

### 3. Confirmed SAFE — timestamps used in prompts come from the sim clock, not wall clock
- **file:line:** `pregame/world/store.py:96-101` (`sim_now`), `pregame/world/store.py:104-134` (`fire_event`, `$max` on the clock, driven by each event's own scripted `event_time`). `drafter.py:257` embeds `ctx['as_of'].isoformat()` in the user prompt — since `as_of` is always `store.sim_now(db)` (`pregame/loop.py:83`), and the clock only advances via scripted event times, two runs from a freshly seeded db produce identical `as_of` values and identical prompt text on this axis.
- Wall-clock `datetime.now(timezone.utc)` calls do exist (`pregame/versions.py:292,397`; `pregame/ledger.py:109`; `pregame/improver.py:218,343`; `pregame/gate.py:74`) for `created_at`/`recorded_at` bookkeeping fields, but I found no place that formats these into prompt text — the one place past-proposal metadata reaches a prompt (`improver.py:406-408`) explicitly excludes `created_at`.

### 4. Medium — duplicate cassette keys: last line wins, silently
- **file:line:** `pregame/llm.py:134-145` (`_load_cassette` iterates the JSONL top-to-bottom, `cache[row["key"]] = row` — plain overwrite).
- If the exact same `(role, model, system, prompt)` is ever recorded twice with two different live answers (e.g., a rerun during rehearsal appended to the same file instead of a fresh one), replay silently serves whichever was recorded **last**, with no warning that two answers existed for one key. For JSON-shaped roles this is unlikely to matter much, but it's a silent-failure mode with zero observability.
- **Smallest fix (~5 min):** in `_load_cassette`, if `row["key"]` is already in `cache` and `row["response"] != cache[row["key"]]["response"]`, log a warning (or refuse to load) naming the role/key. Cheap insurance before stage.

### 5. Live path robustness (`pregame/llm.py:_call_cli`, lines 190-243)
- 300s subprocess timeout per call (line 216) raises `LLMError` on timeout (line 222-223) with **no retry** — this is separate from the one JSON-shape retry in `complete_json` (line 121), which only fires when the reply parses but isn't valid JSON. A CLI timeout, non-zero exit, or `is_error` result (lines 230-241) propagates immediately as an exception with zero retries.
- Concurrency composes two limits: oracle's `ThreadPoolExecutor(max_workers=8)` (`oracle.py:21,511`) submits up to 8 grading jobs at once, but each job's CLI call blocks on `self._cli_slots` (`BoundedSemaphore(3)`, `llm.py:87,217`) — so at most 3 `claude` processes run concurrently regardless of how many oracle threads are queued, which is good for rate limits but means 8 jobs serialize through 3 slots (extends wall time, doesn't break correctness).
- One malformed/erroring reply mid-`evaluate_grades` raises out of `pool.map()` (`oracle.py:512`) and aborts the whole batch for that call — I did not have time to trace whether `pregame/gate.py`'s `eval_runs` cache commits per-scenario or in one batch, so I can't confirm/deny partial-cache-row corruption on a mid-batch failure; **flagging as open, worth 5-10 min to check `gate.py`'s eval-cache write timing before relying on a cold live gate run on stage** (the earlier audit already recommends never running a cold live gate on stage — consistent with this).

## Q4 — smallest deterministic-replay rehearsal check (one command)
Add a tiny script (no Atlas, mongomock only) that: seeds a fresh db in fake mode, monkeypatches `LLM.complete_json`/`_cassette_key` to just log `(role, key)` instead of calling `_call`, runs `pregame.loop.run_demo` twice against two independent fresh dbs, and diffs the two ordered `(role, key)` lists. Any diff = a spot where replay will miss. (This is exactly the harness used to find finding #1 above — it took under a minute to write and run once the id chain was suspected.) This should become a pre-stage CI-style check: **run it once right after the fix in Finding #1, before re-recording the real cassette.**
