Pregame · the final system, 26 September 2026

Pregame Architecture

Pregame writes prep briefs for a financial advisor before each client meeting, from facts that keep the date they became true, so last quarter's figure is not repeated as current. Three Claude models each do one job: Claude Sonnet 5 writes the brief, Claude Haiku 4.5 answers the client's questions using only the brief, and Claude Opus 5.5 proposes one change to the harness. Plain code grades, so no model grades its own work. We make two separate claims:

Claim A. A harness, meaning the code around the model, can guarantee things a model alone does not: approved wording, dated and sourced facts, and only the questions the client file calls for.

Claim B. The harness can improve itself safely. It proposes one change at a time, and code adopts the change only if it wins on test meetings the proposer has never seen.

The trust boundary

The proposer is a model with every tool switched off. It only sees text that trusted code chose to show it, so the boundary is what goes into its prompt and what the test gate lets back out.

The proposer sees

  • The advisor's feedback
  • Practice-meeting results, including which questions were missed and why
  • The current settings and an excerpt of the latest brief
  • Its past proposals: adopted or rejected, the reasons in words, the numbers blanked

It never gets

  • The unseen test meetings' records, or their scores as numbers
  • The test questions, grader, scoring rules, audit log or gate code: any proposal touching them is refused before scoring
  • A database connection, or any tool
  • The power to adopt: it can only propose

Honest limits

  • Isolation is enforced by our code inside one program; everything connects as one database user. A separate, read-only database user for the proposer is next.
  • Reasons in words could, over many cycles, let it drift toward the test.
  • 51 of 105 unseen test questions repeat a practice question word for word.

The second test: the teammate's banker book

Our data teammate built a book of one banker, six fictional clients and 24 call preps written by a scripted assistant, a small program (not an AI model) with a busy assistant's careless habits, plus a hidden answer key. Pregame reads it through an adapter.

What MongoDB guarantees

  • The fence. Adopting a change is one multi-document transaction: it advances the version only if none of the four kinds of settings moved since the test, stores the new version, appends the audit entry and closes the proposal, all or nothing (it assumes a single test-gate process).
  • Versions. Every setting is a versioned document with a head pointer, and a rollback is a new version copying an old one by id, so history is never rewritten.
  • Dated facts. Each fact is stored with the date it became true, so the system can ask what was true on any past date.
  • Validators and unique indexes. Validators check the shape of every proposal, version and audit entry; unique indexes make duplicate proposals and forked audit logs impossible.
  • Audit log. Each entry holds a hash of the previous one, so editing, reordering or removing a middle entry is detected; it names briefs by id rather than content, has no secret key, and cannot notice the newest entries being deleted.
  • Score cache. Scores are keyed to the exact settings, the models and a fingerprint of the grading code, so a changed grader never reuses stale scores.
  • Tested on real Atlas. Five opt-in tests on the real cluster check rollback on failure, two racing commits giving exactly one version, validators, duplicates and time round-trips; the last found a real time-zone bug that the in-memory stand-in hid (fixed; the recorded runs were unaffected).

Caveats. Of the model's 9 proposals, 2 were adopted and 7 rejected. The test is small and simulated: 6 unseen test meetings, 35 questions, two simulated households, each meeting run twice, so it detects only large effects. The grader checks words, not meaning, and a reader answering "unknown" everywhere would still get 14 of 35, so scores start near 40%. The fair description is "it won a small simulated test", not "it is proven better".

What you see on stage is a replay of live run C, recorded today. The model's words are recorded, looked up by a fingerprint of the exact prompt, so a changed prompt stops the replay instead of improvising. The test gate, the grading, the MongoDB transaction and the audit log run for real during the replay.

What we learned

  • Enforce in code, don't suggest. Told that both holders share the account, Sonnet still named one decision maker in most preps; once code wrote that claim, as it already writes the disclosures, the same recorded outputs went from 7.5 to 10 of 10 expected actions.
  • Structure over word patterns for safety. The word-pattern checks raised 34 flags on compliant live prose, all false alarms, and cost real improvements; we fixed them and an independent GPT-5.6 Sol review sent the fix back twice. They remain a backstop, while code-inserted disclosures and the exact source and date checks are guarantees.
  • Test what you claim. A strong model alone didn't need the harness to avoid the scripted assistant's mistakes, so on this book the harness adds guarantees and focus, not accuracy.
